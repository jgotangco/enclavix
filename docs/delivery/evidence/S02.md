## Implementation and approved policy
[ADR 0005](../../architecture/adr/0005-identity-and-access.md) specifies the trust boundaries and [security runbook](../../security-and-access.md) describes account approval, recovery, support and containment. Production account services are distinct from mock business portals.

D07 was explicitly approved by Jerome Gotangco: “Use this policy” in response to MFA for all staff/administrator roles, individual accounts, immediate membership revocation, and support disabled until explicitly approved and time-limited. This approves that security policy only, not hosting, spending or deployment.

- IAM 01: provider-verified email/password identity, PKCE web flows, approval/invitations, recovery, provider rate limits, fixed authorization lifetimes and live revocation checks. Accounts alone grant no property access.
- IAM 02: demo cookies and client metadata have no real identity/role authority; forged requests and extra payload fields are denied.
- IAM 03: per-request provider verification and trusted database resolution; a NOLOGIN/NOBYPASSRLS read role, explicit command checks, private schema/table ACLs, scoped references and clean/audience-scoped file downloads. Direct client object reads/uploads/signed URL creation remain denied.
- IAM 04: real TOTP for every staff role; eight-hour resident, one-hour staff, thirty-minute guard absolute authorization lifetimes; recent MFA sign-in for sensitive changes; own-session inventory, selected-session removal and provider sign-out. Refresh does not reset session age.
- IAM 05: civic titles are separate from effective system grants; no self-elevation; actor/reason/scope audit; permission mutation and audit/operation completion are atomic. Identical keyed retries have no second effect; different content conflicts.
- IAM 06: registered operators have no routine access. A different association administrator may approve metadata-only support for at most sixty minutes with reason/audit; expiry, explicit revocation or loss of approver authority ends access. Emergency impersonation is disabled.
- IAM 07: association/community/role contexts come from protected records; property reads are reauthorized; context switches, failures and sign-out clear tenant-specific client state. Android-style HTTP requests use the same boundaries; the Android app/device work remains S06/S07.

## Review corrections
CI surfaced Supabase's non-superuser function-ownership requirements; the migration grants the read role only to its database migration administrator and removes temporary schema CREATE after ownership transfer. An exposed RPC now accepts a text role and validates/casts internally, avoiding client access to private enum/schema definitions. Container verification explicitly injects runtime public configuration. Native logout calls the provider with the actual bearer token rather than relying on absent cookie/session storage. These repairs are included in the successful code run above.

## Data and release impact
One additive S02 migration extends grants/document audience and adds applications, invitations, registered operators and support grants. Generated types cover 21 app tables. Existing migrations and prototype data are not rewritten. The private bucket is created only in disposable verification; no hosted project, resident import, deployment, finance service, worker or Android app was enabled.

Direct client signed links are prohibited so they cannot outlive membership revocation. The download gateway authorizes live metadata then uses a server-only storage key, returns an attachment/no-store response and enforces a 20 MiB foundation bound. Default audience is administrator-only; owner/representative versus occupant evidence is explicit. Upload/scanning/version/retention workflows remain S05. Never classify a real upload as clean using test fixture SQL.

A rollback is a reviewed forward repair closing account routes and revoking S02 RPC execution, preserving identity, audit and operation records. First administrator and operator provisioning require controlled bootstrap and verified authority before real onboarding.
